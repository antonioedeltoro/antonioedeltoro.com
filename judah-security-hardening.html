Case study

Judah Security

October 29, 2026 AuthCSPTrusted TypesXSSAPI securitySPF / DMARCCAADNSSEC

Judah Security is a lead-generation site I built for a Los Angeles security guard and firearms training company. The link opens my portfolio copy of the site.

The project

  • Quote requests for guard services: site address, schedule, number of guards, armed or unarmed.
  • Course inquiries for training classes.
  • News posts managed through an admin editor.
  • Client reviews with reviewer accounts.
  • Stack: a React and Vite front end, and a Node, Express and MongoDB API, hosted on Render.

Security

It has a backend, an admin area and user accounts, so I audited and hardened it end to end.

A+

140 / 100 on Mozilla’s HTTP Observatory, 12 of 12 tests passed, on both the client’s domain and the portfolio copy (baseline before this work: D, 35/100, 3 tests failed). View the live report.

01Threat model

The forms collect sensitive operational details — site addresses, schedules, number of guards, armed or unarmed — so this site has more to protect than a brochure:

  • Account takeover of the admin area or reviewer accounts.
  • Content tampering and stored XSS — a malicious news post running script for every visitor.
  • Spam and abuse of the public endpoints.
  • Lead data exposure.
  • The usual web risks: clickjacking, protocol downgrade, email spoofing and mis-issued certificates.

02Starting point

The baseline scan was a D, 35/100, with 3 tests failed: no Content Security Policy, no HSTS and no X-Frame-Options. The only security header present was X-Content-Type-Options.

03What the audit found

Most severe first:

  1. The admin credential was in the public JavaScript. It lived in a build variable with Vite’s VITE_ prefix, and Vite inlines those into the bundle at build time. The API accepted that same static token, and the admin “login” was a string comparison in the browser. Anyone reading the bundle could create, edit or delete news posts and upload any file type — and because posts were rendered with dangerouslySetInnerHTML, a tampered post could have run script for every visitor. I contained it before fixing it: I removed the variables from the hosting environment so the API rejected the token before the code fix shipped, confirmed the old token was refused, and checked the content for tampering. None was found.
  2. Every lead was bouncing. Both forms opened a mailto: link to an address on a domain with no mail server (no MX record), so quote requests and course inquiries never arrived. I pointed both forms at the client’s real inbox.
  3. The portfolio copy was the production site. The portfolio subdomain was just a second hostname on the production front end, dependent on the client’s API — and its News page was empty because the API’s CORS policy rejected that origin. I rebuilt it as a self-contained copy (section 09).
  4. CORS was reopened by configuration. A CORS setting in the API’s hosting environment re-allowed http://localhost:5173 in production, undoing the allowlist in the code.
  5. A data-integrity bug. Invalid review ratings were silently saved as five stars.

04Authentication

  • Admin auth moved to the server. The admin password is stored only as a bcrypt hash on the server. Logging in returns a short-lived JWT (two hours), signed with a secret separate from the reviewer tokens and scoped by audience, so a reviewer token can never act as admin.
  • Brute-force protection. Login attempts are tightly rate-limited per IP.
  • Token storage. Old tokens are purged from browser storage, and admin and reviewer tokens moved from localStorage to sessionStorage, so they don’t outlive the tab.

05The API

  • Abuse limits. Rate limits on every route, with tighter limits on authentication and review writes, and a small request-body limit.
  • Validation. Input validation and length caps on every write; invalid ratings are now rejected instead of saved.
  • Lead data stays out of logs. Request bodies are no longer logged.
  • Uploads. Limited to JPEG, PNG and WebP up to 5 MB, saved under random filenames, and served with nosniff and a sandboxed CSP.
  • CORS. An exact-match allowlist with no credentials.
  • Headers. Helmet with a deny-all CSP (the API only returns JSON) and two-year HSTS.
  • No configuration leaks. The health endpoint no longer exposes the CORS allowlist.
  • Dependencies. npm audit reports zero vulnerabilities on the backend.

06Front end: deny-by-default CSP and Trusted Types

The core of the policy, with the API’s origin replaced by a placeholder:

default-src 'none';
script-src 'self'; style-src 'self'; font-src 'self';
connect-src <api-origin>;
frame-ancestors 'none';
require-trusted-types-for 'script'; trusted-types 'none';

Enforcing Trusted Types with no policies at all means the browser refuses to turn any string into HTML or script. Getting there took four changes:

  • No more dangerouslySetInnerHTML. News bodies are stored as HTML, so I wrote a small whitelist renderer that turns paragraphs, bold text and lists into React elements. No HTML string ever reaches the DOM.
  • Inline styles moved into CSS, so style-src needs nothing beyond 'self'.
  • Four unused dependencies removed: axios, EmailJS, Font Awesome and react-helmet.
  • No third-party asset origins — every script, style and font is served by the site itself.

08Domain and accounts

The domain sends and receives no mail, so the records say exactly that:

@        TXT  "v=spf1 -all"
_dmarc   TXT  "v=DMARC1; p=none;"
@        CAA  0 issue "letsencrypt.org"
@        CAA  0 issue "pki.goog"
  • DMARC starts at p=none to watch the reports before tightening.
  • CAA is limited to the host’s two certificate authorities, Let’s Encrypt and Google Trust Services. Listing only one would break a future renewal through the other.
  • DNSSEC is enabled and validating.
  • Accounts: multi-factor authentication on the hosting, Git and registrar accounts.

09The portfolio copy

The portfolio copy is a separate build mode of the same codebase, so it inherits every fix above. It:

  • Makes zero API calls. It snapshots the live content into the bundle, checksum-verified.
  • Has no admin area, and shows the forms and reviews read-only, with a “portfolio copy” banner.
  • Stays out of search. It’s noindex with its own canonical, so it never competes with the client’s site.
  • Has an even tighter CSP. The API origin is gone entirely: connect-src 'self'.
  • Runs on its own, as a separate static site on the portfolio subdomain, independent of the client’s API and database.

10Rollout and verification

The rule throughout: never tighten a header before the code that needs it is live. The code shipped first with a strict <meta> CSP; the header CSP and Trusted Types came only after that code was in production.

  • Before deploying: headless Chromium crawled every route of both builds on desktop and mobile and asserted zero CSP or Trusted Types violations, zero JavaScript errors and zero third-party requests. Injected <img onerror> and <script> payloads rendered as plain text, framing was blocked, and the admin login flow worked.
  • After deploying: the live bundle’s hash matched the tested build, the headers were checked live, Observatory re-scanned every hostname, and every DNS record was confirmed through a public DNSSEC-validating resolver.

11What’s next

  • DMARC enforcement: move to p=reject once the reports are clean.
  • Dependency upgrades: move the front-end tooling across major versions; the remaining advisories are mostly in development-only tooling.
  • Account security stays the main ongoing control.

Caso de estudio

Judah Security

29 de octubre de 2026 AutenticaciónCSPTrusted TypesXSSSeguridad de APISPF / DMARCCAADNSSEC

Judah Security es un sitio de captación de clientes que desarrollé para una empresa de guardias de seguridad y capacitación en armas de fuego en Los Ángeles. El enlace abre mi copia del sitio para el portafolio.

El proyecto

  • Solicitudes de cotización de servicios de guardias: dirección del lugar, horarios, número de guardias, armados o desarmados.
  • Consultas sobre cursos de capacitación.
  • Noticias administradas desde un editor privado.
  • Reseñas de clientes con cuentas de usuario.
  • Stack: un front end en React y Vite, y una API en Node, Express y MongoDB, alojados en Render.

Seguridad

Tiene backend, un área de administración y cuentas de usuario, así que lo audité y lo protegí de principio a fin.

A+

140 / 100 en el HTTP Observatory de Mozilla, 12 de 12 pruebas superadas, tanto en el dominio del cliente como en la copia del portafolio (punto de partida antes de este trabajo: D, 35/100, 3 pruebas reprobadas). Ver el informe en vivo.

01Modelo de amenazas

Los formularios recogen datos operativos delicados (direcciones de los sitios, horarios, número de guardias, si van armados o no), así que este sitio tiene más que proteger que un simple folleto:

  • Toma de control de cuentas: el área de administración o las cuentas de quienes dejan reseñas.
  • Alteración de contenido y XSS almacenado: una noticia maliciosa que ejecute código en el navegador de cada visitante.
  • Spam y abuso de los endpoints públicos.
  • Exposición de los datos de los clientes potenciales.
  • Los riesgos web de siempre: clickjacking, degradación de protocolo, suplantación de correo y certificados emitidos indebidamente.

02Punto de partida

El análisis de referencia dio una D, 35/100, con 3 pruebas reprobadas: sin Política de Seguridad de Contenido, sin HSTS y sin X-Frame-Options. El único encabezado de seguridad presente era X-Content-Type-Options.

03Lo que encontró la auditoría

De mayor a menor gravedad:

  1. La credencial de administrador estaba en el JavaScript público. Estaba en una variable de compilación con el prefijo VITE_, y Vite incrusta esas variables en el paquete público al compilar. La API aceptaba ese mismo token fijo, y el «inicio de sesión» de administrador era una simple comparación de cadenas en el navegador. Cualquiera que leyera el paquete podía crear, editar o borrar noticias y subir archivos de cualquier tipo; y como las noticias se mostraban con dangerouslySetInnerHTML, una noticia alterada podía ejecutar código para todos los visitantes. Primero contuve el problema y después lo corregí: eliminé las variables del entorno de alojamiento para que la API rechazara el token antes de publicar la corrección, confirmé que el token anterior ya no funcionaba y revisé el contenido en busca de alteraciones. No había ninguna.
  2. Todas las solicitudes rebotaban. Los dos formularios abrían un enlace mailto: hacia una dirección de un dominio sin servidor de correo (sin registro MX), así que ni las cotizaciones ni las consultas sobre cursos llegaban a su destino. Redirigí ambos formularios al buzón real del cliente.
  3. La copia del portafolio era el sitio de producción. El subdominio del portafolio era solo un segundo nombre del front end de producción, dependiente de la API del cliente, y su página de noticias aparecía vacía porque la política CORS de la API rechazaba ese origen. La reconstruí como una copia independiente (sección 09).
  4. La configuración volvía a abrir CORS. Un ajuste de CORS en el entorno de alojamiento de la API volvía a permitir http://localhost:5173 en producción, lo que anulaba la lista de orígenes permitidos definida en el código.
  5. Un error de integridad de datos. Las calificaciones no válidas de las reseñas se guardaban, sin aviso, como cinco estrellas.

04Autenticación

  • La autenticación de administrador pasó al servidor. La contraseña de administrador solo se guarda como un hash bcrypt en el servidor. Al iniciar sesión se emite un JWT de corta duración (dos horas), firmado con un secreto distinto del de las reseñas y limitado por audiencia, de modo que un token de reseña nunca puede actuar como administrador.
  • Protección contra fuerza bruta. Los intentos de inicio de sesión tienen un límite estricto por IP.
  • Almacenamiento de tokens. Se eliminan los tokens antiguos del navegador, y los de administrador y de reseñas pasaron de localStorage a sessionStorage, así que no sobreviven al cerrar la pestaña.

05La API

  • Límites contra el abuso. Límites de solicitudes en todas las rutas, más estrictos en la autenticación y en la escritura de reseñas, y un tamaño máximo reducido para el cuerpo de las solicitudes.
  • Validación. Validación de datos y longitudes máximas en todas las escrituras; las calificaciones no válidas ahora se rechazan en lugar de guardarse.
  • Los datos de los clientes no llegan a los registros. Ya no se registra el cuerpo de las solicitudes.
  • Archivos subidos. Solo JPEG, PNG y WebP de hasta 5 MB, guardados con nombres aleatorios y servidos con nosniff y una CSP aislada (sandbox).
  • CORS. Una lista de orígenes con coincidencia exacta y sin credenciales.
  • Encabezados. Helmet con una CSP que lo deniega todo (la API solo devuelve JSON) y HSTS de dos años.
  • Sin filtrar la configuración. El endpoint de estado ya no expone la lista de orígenes de CORS.
  • Dependencias. npm audit no reporta ninguna vulnerabilidad en el backend.

06Front end: CSP que deniega por defecto y Trusted Types

El núcleo de la política, con el origen de la API sustituido por un marcador de posición:

default-src 'none';
script-src 'self'; style-src 'self'; font-src 'self';
connect-src <api-origin>;
frame-ancestors 'none';
require-trusted-types-for 'script'; trusted-types 'none';

Aplicar Trusted Types sin ninguna política significa que el navegador se niega a convertir cualquier cadena de texto en HTML o en script. Para llegar ahí hicieron falta cuatro cambios:

  • Adiós a dangerouslySetInnerHTML. El cuerpo de las noticias se guarda como HTML, así que escribí un pequeño renderizador con lista blanca que convierte párrafos, negritas y listas en elementos de React. Ninguna cadena HTML llega nunca al DOM.
  • Los estilos en línea pasaron a CSS, así que style-src no necesita nada más que 'self'.
  • Se eliminaron cuatro dependencias sin uso: axios, EmailJS, Font Awesome y react-helmet.
  • Ningún recurso de terceros: el propio sitio sirve todos los scripts, estilos y fuentes.

08Dominio y cuentas

El dominio no envía ni recibe correo, y los registros lo declaran así:

@        TXT  "v=spf1 -all"
_dmarc   TXT  "v=DMARC1; p=none;"
@        CAA  0 issue "letsencrypt.org"
@        CAA  0 issue "pki.goog"
  • DMARC empieza en p=none para revisar los informes antes de endurecer la política.
  • CAA se limita a las dos autoridades de certificación que usa el proveedor: Let’s Encrypt y Google Trust Services. Incluir solo una haría fallar una renovación futura a través de la otra.
  • DNSSEC está activado y validando.
  • Cuentas: autenticación multifactor en las cuentas de alojamiento, Git y el registrador.

09La copia del portafolio

La copia del portafolio es un modo de compilación aparte del mismo código, así que hereda todas las correcciones anteriores. Esta copia:

  • No hace ninguna llamada a la API. Incluye en el paquete una instantánea del contenido en vivo, verificada con suma de comprobación.
  • No tiene área de administración, y muestra los formularios y las reseñas en modo de solo lectura, con un aviso de «copia del portafolio».
  • No aparece en los buscadores. Lleva noindex y su propia URL canónica, para no competir nunca con el sitio del cliente.
  • Tiene una CSP todavía más estricta. El origen de la API desaparece por completo: connect-src 'self'.
  • Funciona por su cuenta, como un sitio estático independiente en el subdominio del portafolio, sin depender de la API ni de la base de datos del cliente.

10Implementación y verificación

La regla en todo momento: nunca endurecer un encabezado antes de que esté en producción el código que lo necesita. Primero se publicó el código con una CSP estricta en la etiqueta <meta>; la CSP del encabezado y Trusted Types llegaron solo cuando ese código ya estaba en producción.

  • Antes del despliegue: Chromium sin interfaz recorrió todas las rutas de ambas compilaciones, en escritorio y en móvil, y verificó que no hubiera ninguna violación de la CSP ni de Trusted Types, ningún error de JavaScript ni ninguna solicitud a terceros. Las cargas inyectadas con <img onerror> y <script> se mostraron como texto plano, el sitio no se pudo incrustar en otro y el inicio de sesión de administrador funcionó.
  • Después del despliegue: el hash del paquete en vivo coincidió con el de la compilación probada, se revisaron los encabezados en vivo, Observatory volvió a analizar cada nombre de dominio y cada registro DNS se confirmó mediante un resolutor público que valida DNSSEC.

11Próximos pasos

  • Aplicación de DMARC: pasar a p=reject cuando los informes estén limpios.
  • Actualización de dependencias: llevar las herramientas del front end a sus nuevas versiones mayores; los avisos que quedan son, en su mayoría, de herramientas de desarrollo.
  • La seguridad de las cuentas sigue siendo el principal control de aquí en adelante.
