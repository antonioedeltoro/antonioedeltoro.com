Faby Services

fabyservices.com is the site for Faby Services, a bilingual tax, insurance, bookkeeping and notary office in Moreno Valley, California, and a client of mine through deltoro.codes.

The project

  • Service pages for taxes, insurance, bookkeeping and notary work, plus seasonal pages for tax season and health-insurance open enrollment.
  • Appointment requests through a form, and a contact page with an interactive Mapbox map.
  • News posts managed through an admin editor, and client reviews from signed-in users.
  • Bilingual in English and Spanish, with light and dark themes.
  • Stack: a React and Vite front end, and a Node, Express and MongoDB API.

Security

Its HTTP headers already scored A+, so this pass went after everything a header scanner can’t see: the domain, email, the accounts behind the site, and the database. That’s also where the most serious finding turned up.

A+

125 / 100 on Mozilla’s HTTP Observatory, 12 of 12 tests passed, before and after this pass. The score didn’t move, by design: this work hardened layers Observatory doesn’t score. View the live report.

01Context

The site is a static React/Vite front end on a managed host behind a CDN, a small Node/Express API, and a hosted MongoDB database. An earlier pass had already taken the front end’s HTTP security headers to an A+. This pass covered what Observatory doesn’t measure: the domain, email, the accounts behind the site, and the database.

One detail shaped the rest of the work: the business’s email runs on a personal webmail account, not on the domain. The domain itself sends no mail.

02Threat model

A tax and insurance brand is a prime phishing target, so the domain and the accounts matter as much as the pages:

  • Email spoofing: phishing sent “from” the business’s domain.
  • Mis-issued TLS certificates for the domain.
  • DNS tampering: forged answers that send visitors somewhere else.
  • Account takeover of the code host, the hosting provider or the registrar, any of which means full control of the site.
  • Exposed database credentials.

03Starting point

The baseline scan was A+, 125/100, 12 of 12 tests passed. The headers were in good shape; what surrounded them wasn’t:

  • No SPF, DKIM, DMARC or CAA records, and DNSSEC was off.
  • A stray IPv6 (AAAA) record that wasn’t part of the host’s setup.
  • Leftover MX records from a registrar migration, pointing to a hosted mail service the client never signed up for.

04Domain: declaring “this domain sends no mail”

The final records:

@        TXT  "v=spf1 -all"
_dmarc   TXT  "v=DMARC1; p=reject;"
@        CAA  0 issue "letsencrypt.org"
@        CAA  0 issue "pki.goog"
  • The policy changed along the way. SPF started out authorizing a mail provider with a softfail, with DMARC in a monitoring phase. Once I confirmed the domain sends nothing at all, I switched to the strict no-mail posture: SPF -all and DMARC p=reject. Lesson: find out who actually sends mail before you design the policy.
  • CAA lists both certificate authorities the host issues from, so a renewal through either one won’t fail without warning. The www hostname is a CNAME into the host, so the apex CAA record covers it too.
  • DNSSEC is now on at the registrar, which also hosts DNS, and was confirmed through a public validating resolver.
  • Cleanup. I removed the stray AAAA record and all of the leftover MX records, so the domain now neither sends nor receives mail. A null MX (0 .) to declare that formally was rejected by the DNS provider’s interface; SPF -all and DMARC p=reject already cover the spoofing risk, so the gap is documented rather than worked around.

05Accounts

Two-factor authentication is on for every account that controls the site:

  • Code host: authenticator app, mobile app and a passkey, with recovery codes stored offline. This one came first: the host deploys automatically from the repository, so whoever controls the repo controls the live site.
  • Hosting provider.
  • Registrar, with account recovery configured. Its two-factor currently uses SMS; the plan is to move it to an authenticator app.
  • Database provider.

The client’s own mailbox. The business’s email lives on a personal webmail account, not on the domain, so it’s the account that matters most to the business. It’s also the client’s to secure, not mine. I sent the client a written request, in Spanish, to turn on 2-Step Verification with an authenticator app or a passkey rather than SMS. Everything I control is hardened, and the one account I don’t is covered by a documented request.

06The finding: exposed database credentials

While auditing, I found an old automated alert from the database provider: live database credentials had at one point been committed to the repository. They were no longer in the Git history, but the values themselves were still valid, and the database accepted connections from any IP address (0.0.0.0/0). Rotating them came first.

The response, in order:

  1. Rotate the database password. I changed the database user’s password and updated it on the host, so the leaked value stopped working.
  2. Rotate the other secrets in the same change. Every other secret the app uses was rotated too, which signed out all existing sessions, by design. I also removed unused credentials left over from an abandoned image-hosting experiment that was never deployed, so the local configuration now matches exactly what production uses.
  3. Close network access. I replaced the open-to-all rule with an allow-list of the host’s two published outbound IP ranges plus a single developer IP. Both ranges went in before the open-to-all rule came out, so the API never lost database access.
  4. Scan the entire history. I searched every commit for secret patterns (credentials embedded in connection strings, private keys, and common cloud, payment and API token formats), printing only where a match was, never its value. The only matches were placeholder values, not real secrets.
  5. Verify after every step. The API logs showed a clean database connection, the public endpoints returned their data, sign-in worked with the new credentials, and no data was lost.

What this taught me:

  • Rotation is what makes an exposed secret harmless. Removing it from the repository doesn’t invalidate it; changing it does.
  • Prevention beats detection. Push protection stops a secret before it ever reaches the repository.
  • Network restrictions are a second lock. With access limited to known addresses, a leaked password alone isn’t enough to get in.

07Verification

  • Every DNS record confirmed through a public DNSSEC-validating resolver.
  • Each account’s two-factor status checked in that account’s own security settings.
  • API health and site data checked after each deploy.
  • Observatory re-scanned: still A+, 125/100, 12 of 12. Unchanged by design, because this pass hardened layers Observatory doesn’t score.

08What I’d do next

  • Registrar two-factor: move it from SMS to an authenticator app.
  • Network access: prune the legacy entries from the database’s IP allow-list.
  • Push protection and secret scanning on the repository, so a secret committed by mistake is blocked at push time instead of caught afterward.
  • Optional: a deny-by-default CSP (default-src 'none') for Observatory’s last bonus points.

Faby Services

29 de octubre de 2026 DNSSECSPF / DMARCCAAMFARotación de secretosAcceso de red

fabyservices.com es el sitio de Faby Services, una oficina bilingüe de impuestos, seguros, contabilidad y notaría en Moreno Valley, California, y cliente mío a través de deltoro.codes.

El proyecto

  • Páginas de servicios de impuestos, seguros, contabilidad y notaría, además de páginas de temporada para la declaración de impuestos y la inscripción abierta de seguros médicos.
  • Solicitudes de cita mediante un formulario, y una página de contacto con un mapa interactivo de Mapbox.
  • Noticias administradas desde un editor privado, y reseñas de clientes de usuarios registrados.
  • Bilingüe en inglés y español, con temas claro y oscuro.
  • Stack: un front end en React y Vite, y una API en Node, Express y MongoDB.

Seguridad

Sus encabezados HTTP ya tenían A+, así que esta vez el trabajo se centró en todo lo que un escáner de encabezados no ve: el dominio, el correo, las cuentas detrás del sitio y la base de datos. Ahí fue también donde apareció el hallazgo más serio.

A+

125 / 100 en el HTTP Observatory de Mozilla, 12 de 12 pruebas superadas, antes y después de este trabajo. La puntuación no cambió, y era de esperar: esta vez se reforzaron capas que Observatory no evalúa. Ver el informe en vivo.

01Contexto

El sitio consta de un front end estático en React/Vite, alojado en un servicio administrado detrás de una CDN; una pequeña API en Node/Express, y una base de datos MongoDB en la nube. En una etapa anterior, los encabezados de seguridad HTTP del front end ya habían alcanzado una calificación A+. Esta etapa abarcó lo que Observatory no mide: el dominio, el correo, las cuentas detrás del sitio y la base de datos.

Un detalle definió el resto del trabajo: el correo del negocio funciona en una cuenta de correo web personal, no en el dominio. El dominio en sí no envía correo.

02Modelo de amenazas

Una marca de impuestos y seguros es un blanco ideal para el phishing, así que el dominio y las cuentas importan tanto como las páginas:

  • Suplantación de correo: phishing enviado «desde» el dominio del negocio.
  • Certificados TLS emitidos indebidamente para el dominio.
  • Manipulación del DNS: respuestas falsificadas que desvían a los visitantes a otro lugar.
  • Toma de control de cuentas: el alojamiento del código, el proveedor de alojamiento o el registrador; cualquiera de ellas da control total sobre el sitio.
  • Credenciales de la base de datos expuestas.

03Punto de partida

El análisis de referencia dio A+, 125/100, 12 de 12 pruebas superadas. Los encabezados estaban en buena forma; lo que los rodeaba, no:

  • Sin registros SPF, DKIM, DMARC ni CAA, y con DNSSEC desactivado.
  • Un registro IPv6 (AAAA) suelto que no formaba parte de la configuración del proveedor.
  • Registros MX sobrantes de una migración de registrador, que apuntaban a un servicio de correo alojado que el cliente nunca contrató.

04Dominio: declarar que «este dominio no envía correo»

Los registros finales:

@        TXT  "v=spf1 -all"
_dmarc   TXT  "v=DMARC1; p=reject;"
@        CAA  0 issue "letsencrypt.org"
@        CAA  0 issue "pki.goog"
  • La política cambió sobre la marcha. Al principio, el SPF autorizaba a un proveedor de correo con un fallo suave (softfail), y DMARC estaba en fase de monitoreo. Cuando confirmé que el dominio no envía absolutamente nada, pasé a la postura estricta de «sin correo»: SPF -all y DMARC p=reject. Lección: primero hay que averiguar quién envía correo realmente y después diseñar la política.
  • CAA incluye las dos autoridades de certificación que usa el proveedor, para que una renovación a través de cualquiera de ellas no falle sin aviso. El nombre www es un CNAME que apunta al proveedor, así que el registro CAA del dominio raíz también lo cubre.
  • DNSSEC quedó activado en el registrador, que también aloja el DNS, y se confirmó mediante un resolutor público que valida DNSSEC.
  • Limpieza. Eliminé el registro AAAA suelto y todos los registros MX sobrantes, así que ahora el dominio no envía ni recibe correo. La interfaz del proveedor de DNS rechazó un MX nulo (0 .) para declararlo formalmente; como SPF -all y DMARC p=reject ya cubren el riesgo de suplantación, dejé documentada esa limitación en lugar de buscarle un rodeo.

05Cuentas

La autenticación de dos factores está activada en todas las cuentas que controlan el sitio:

  • Alojamiento del código: aplicación de autenticación, aplicación móvil y una llave de acceso (passkey), con los códigos de recuperación guardados fuera de línea. Esta fue la primera: el proveedor despliega automáticamente desde el repositorio, así que quien controle el repositorio controla el sitio en vivo.
  • Proveedor de alojamiento.
  • Registrador, con la recuperación de la cuenta configurada. Por ahora su segundo factor usa SMS; el plan es cambiarlo a una aplicación de autenticación.
  • Proveedor de la base de datos.

El buzón del propio cliente. El correo del negocio está en una cuenta de correo web personal, no en el dominio, así que es la cuenta más importante para el negocio, y protegerla le corresponde al cliente, no a mí. Le envié una solicitud por escrito, en español, para que active la verificación en dos pasos con una aplicación de autenticación o una llave de acceso (passkey) en lugar de SMS. Todo lo que está bajo mi control quedó reforzado, y la única cuenta que no lo está queda cubierta por una solicitud documentada.

06El hallazgo: credenciales de la base de datos expuestas

Durante la auditoría encontré una alerta automática antigua del proveedor de la base de datos: en algún momento, unas credenciales reales de la base de datos se habían subido al repositorio. Ya no estaban en el historial de Git, pero los valores seguían siendo válidos, y la base de datos aceptaba conexiones desde cualquier dirección IP (0.0.0.0/0). Lo primero fue rotarlas.

La respuesta, en este orden:

  1. Cambiar la contraseña de la base de datos. Cambié la contraseña del usuario de la base de datos y la actualicé en el proveedor de alojamiento, de modo que el valor filtrado dejó de funcionar.
  2. Rotar los demás secretos en el mismo cambio. También se rotaron todos los demás secretos de la aplicación, lo que cerró todas las sesiones abiertas, a propósito. Además, eliminé unas credenciales sin uso que quedaban de un experimento de alojamiento de imágenes que nunca se desplegó, así que la configuración local ahora coincide exactamente con la de producción.
  3. Cerrar el acceso de red. Sustituí la regla abierta a todos por una lista que solo permite los dos rangos de IP de salida que publica el proveedor de alojamiento, más una sola IP de desarrollo. Ambos rangos se agregaron antes de quitar la regla abierta a todos, así que la API nunca perdió el acceso a la base de datos.
  4. Revisar todo el historial. Busqué patrones de secretos en cada commit (credenciales incrustadas en cadenas de conexión, claves privadas y formatos comunes de tokens de servicios en la nube, de pago y de API), mostrando solo dónde había una coincidencia, nunca su valor. Las únicas coincidencias fueron valores de ejemplo, no secretos reales.
  5. Verificar después de cada paso. Los registros de la API mostraron una conexión limpia con la base de datos, los endpoints públicos devolvieron sus datos, el inicio de sesión funcionó con las nuevas credenciales y no se perdieron datos.

Lo que aprendí:

  • Lo que vuelve inofensivo un secreto expuesto es rotarlo. Quitarlo del repositorio no lo invalida; cambiarlo, sí.
  • Más vale prevenir que detectar. La protección de push detiene un secreto antes de que llegue al repositorio.
  • Restringir la red es un segundo candado. Con el acceso limitado a direcciones conocidas, una contraseña filtrada por sí sola no basta para entrar.

07Verificación

  • Cada registro DNS se confirmó mediante un resolutor público que valida DNSSEC.
  • El estado de la autenticación de dos factores de cada cuenta se revisó en la configuración de seguridad de esa misma cuenta.
  • El estado de la API y los datos del sitio se revisaron después de cada despliegue.
  • Nuevo análisis en Observatory: sigue en A+, 125/100, 12 de 12. Sin cambios, y era de esperar, porque esta etapa reforzó capas que Observatory no evalúa.

08Próximos pasos

  • Segundo factor del registrador: pasarlo de SMS a una aplicación de autenticación.
  • Acceso de red: depurar las entradas antiguas de la lista de IP permitidas de la base de datos.
  • Protección de push y escaneo de secretos en el repositorio, para que un secreto subido por error se bloquee al hacer push en lugar de detectarse después.
  • Opcional: una CSP que deniegue por defecto (default-src 'none') para obtener los últimos puntos adicionales de Observatory.
