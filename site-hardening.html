antonioedeltoro.com is my personal portfolio, the site you’re reading now.

The project

  • Hand-written HTML, CSS and JavaScript, with no framework and no build step.
  • Bilingual (English and Spanish), with light and dark themes applied before the page paints.
  • Shared navigation and footer, built by one script for every page.
  • Self-hosted fonts and icons.
  • Hosting: a Render static site, with DNS at Squarespace.

Security

It’s a static site: no backend, no database, no logins. That makes it a small target, but not a zero one. I treated it like a production asset and hardened it end to end: the page, the server responses, and the domain itself.

A+

140 / 100 on Mozilla’s HTTP Observatory, 12 of 12 tests passed. The score above 100 comes from bonus points that only the strictest configurations earn. View the live report.

01Threat model

With no user data to steal, the realistic risks for a site like this are about integrity and reputation, not data breaches:

  • Script injection through a compromised third-party asset (a font or icon CDN).
  • Clickjacking: the site framed inside a hostile page.
  • Protocol downgrade: a visitor pushed from HTTPS to HTTP on an untrusted network.
  • Email spoofing: phishing sent “from” this domain to recruiters who have seen it on my résumé.
  • Mis-issued certificates: a certificate authority issuing a valid TLS certificate for this domain to someone else.

02Starting point

The site already had a reasonable baseline: HTTPS, a <meta> Content Security Policy, Subresource Integrity on the icon stylesheet, a security.txt, DNSSEC on the domain, and a set of response headers configured at the host. The gaps:

  • Two third-party origins (Google Fonts and jsDelivr) were allowed to serve styles and fonts. Google Fonts serves CSS that varies by browser, so it cannot be pinned with SRI, so that origin was trusted blindly.
  • Every visit disclosed the visitor’s IP address to both providers, which the privacy policy had to call out.
  • The CSP started from default-src 'self' rather than denying by default.
  • The domain had no email authentication records and no CAA record.

03Removing third-party dependencies

The cleanest way to secure a dependency is to not load it from someone else. I self-hosted all three typefaces as WOFF2 files and replaced the full Tabler Icons webfont with a subset containing only the 17 glyphs the site uses:

pyftsubset tabler-icons.ttf --unicodes="U+ea16,U+ea24,…" \
  --flavor=woff2 --no-hinting --layout-features='' \
  --output-file=fonts/tabler-icons-subset.woff2

The icon font went from 462 KB to 3.5 KB. The site now makes zero requests to any origin but its own, and the privacy policy was updated to say so.

04A deny-by-default Content Security Policy

With every asset first-party, the CSP could start from nothing and allow back only what the site actually uses:

default-src 'none';
script-src 'self'; style-src 'self'; font-src 'self';
img-src 'self' data:; manifest-src 'self';
form-action 'self'; base-uri 'none';
object-src 'none'; frame-src 'none'; worker-src 'none';
frame-ancestors 'none';
require-trusted-types-for 'script'; trusted-types 'none';
upgrade-insecure-requests

There are no 'unsafe-inline' or 'unsafe-eval' exceptions; inline styles had already been moved into stylesheets. The policy ships twice: as a <meta> tag in each page and as an HTTP header. That is deliberate: browsers ignore frame-ancestors in a meta tag, so clickjacking protection only works from the header.

The policy also enforces Trusted Types with no policies allowed (trusted-types 'none'). The browser now refuses to turn any string into HTML or script (assigning to innerHTML, outerHTML or a script’s text throws an error), which shuts down DOM-based XSS as a class rather than one bug at a time. Getting there meant removing every such sink from the site’s own code: the shared nav and footer are now built with DOM APIs, and the language toggle, which used to swap copy with innerHTML, now ships both languages as static markup and lets CSS show the active one.

06Domain: email and certificates

This domain never sends or receives email, so the right policy is to say so publicly:

@        TXT  "v=spf1 -all"
_dmarc   TXT  "v=DMARC1; p=reject;"
@        CAA  0 issue "letsencrypt.org"
@        CAA  0 issue "pki.goog"
  • SPF -all authorizes no server to send mail as the domain.
  • DMARC p=reject tells receiving providers to reject anything that fails, rather than just flag it.
  • CAA limits certificate issuance to the two authorities my host uses. Listing only one would have broken a future renewal through the other.
  • DNSSEC was already on, so these records are signed and can’t be forged in transit.

I also wanted a null MX record (0 .) to declare that the domain accepts no mail. The DNS provider’s interface rejects it. Since SPF and DMARC already cover the spoofing risk, I documented the gap rather than move DNS providers over it.

07Rollout and verification

Order mattered. Tightening the CSP header before the self-hosted assets were deployed would have blocked the old Google Fonts and jsDelivr requests on the live site and broken every font and icon. So the sequence was: ship the code with the strict <meta> CSP, confirm the deploy, then tighten the header. The Trusted Types change followed the same order: the old language toggle relied on innerHTML, so enforcing it in the header before the rewritten code was live would have broken the page.

  • Before deploying: a headless browser loaded every page in light and dark mode, English and Spanish, desktop and mobile, and asserted zero CSP violations, zero JavaScript errors, zero third-party requests, and that every font and icon actually loaded. For the Trusted Types rewrite it also compared the old and new versions side by side (identical visible text, identical toggle behavior) and confirmed the browser now blocks innerHTML outright.
  • After deploying: the live response headers were checked directly, then scored by Mozilla’s HTTP Observatory.
  • DNS: each record was confirmed through a public DNSSEC-validating resolver.

08What I’d do next

  • HSTS preload. Considered and deferred. Preloading is effectively permanent and gains little over a two-year HSTS policy on a site with no logins.
  • Account security. After this work, the weakest link isn’t the site. It’s the accounts behind it. Anyone who controls the Git repository, the host, or the registrar controls the site. All three are behind multi-factor authentication, and that’s where ongoing attention belongs.

Caso de estudio

antonioedeltoro.com

28 de octubre de 2026 CSPEncabezados HTTPDNSSECSPF / DMARCCAATrusted Types

antonioedeltoro.com es mi portafolio personal, el sitio que estás leyendo.

El proyecto

  • HTML, CSS y JavaScript escritos a mano, sin framework y sin paso de compilación.
  • Bilingüe (inglés y español), con temas claro y oscuro que se aplican antes de que se pinte la página.
  • Navegación y pie de página compartidos, generados por un solo script para todas las páginas.
  • Fuentes e íconos alojados en el propio sitio.
  • Alojamiento: sitio estático en Render, con el DNS en Squarespace.

Seguridad

Es un sitio estático: sin backend, sin base de datos, sin inicios de sesión. Eso lo convierte en un objetivo pequeño, pero no nulo. Lo traté como un activo de producción y lo protegí de principio a fin: la página, las respuestas del servidor y el propio dominio.

A+

140 / 100 en el HTTP Observatory de Mozilla, 12 de 12 pruebas superadas. La puntuación por encima de 100 proviene de puntos adicionales que solo obtienen las configuraciones más estrictas. Ver el informe en vivo.

01Modelo de amenazas

Sin datos de usuarios que robar, los riesgos realistas para un sitio como este tienen que ver con la integridad y la reputación, no con filtraciones de datos:

  • Inyección de scripts a través de un recurso de terceros comprometido (una CDN de fuentes o de íconos).
  • Clickjacking: el sitio incrustado dentro de una página maliciosa.
  • Degradación de protocolo: un visitante forzado de HTTPS a HTTP en una red no confiable.
  • Suplantación de correo: phishing enviado «desde» este dominio a reclutadores que lo han visto en mi currículum.
  • Certificados emitidos indebidamente: una autoridad de certificación que emite un certificado TLS válido para este dominio a otra persona.

02Punto de partida

El sitio ya tenía una base razonable: HTTPS, una Política de Seguridad de Contenido (CSP) en una etiqueta <meta>, Integridad de Subrecursos (SRI) en la hoja de estilos de íconos, un archivo security.txt, DNSSEC en el dominio y un conjunto de encabezados configurados en el servidor. Las deficiencias:

  • Dos orígenes de terceros (Google Fonts y jsDelivr) podían servir estilos y fuentes. Google Fonts sirve CSS que varía según el navegador, por lo que no puede fijarse con SRI: se confiaba en ese origen a ciegas.
  • Cada visita revelaba la dirección IP del visitante a ambos proveedores, algo que la política de privacidad tenía que advertir.
  • La CSP partía de default-src 'self' en lugar de denegar todo por defecto.
  • El dominio no tenía registros de autenticación de correo ni registro CAA.

03Eliminación de dependencias de terceros

La forma más limpia de proteger una dependencia es no cargarla desde los servidores de otro. Alojé las tres tipografías en el propio sitio como archivos WOFF2 y reemplacé la fuente completa de Tabler Icons por un subconjunto que contiene solo los 17 glifos que usa el sitio:

pyftsubset tabler-icons.ttf --unicodes="U+ea16,U+ea24,…" \
  --flavor=woff2 --no-hinting --layout-features='' \
  --output-file=fonts/tabler-icons-subset.woff2

La fuente de íconos pasó de 462 KB a 3.5 KB. El sitio ya no hace ninguna solicitud a otro origen que no sea el suyo, y la política de privacidad se actualizó para reflejarlo.

04Una CSP que deniega por defecto

Con todos los recursos alojados en el propio sitio, la CSP pudo partir de cero y permitir únicamente lo que el sitio realmente usa:

default-src 'none';
script-src 'self'; style-src 'self'; font-src 'self';
img-src 'self' data:; manifest-src 'self';
form-action 'self'; base-uri 'none';
object-src 'none'; frame-src 'none'; worker-src 'none';
frame-ancestors 'none';
require-trusted-types-for 'script'; trusted-types 'none';
upgrade-insecure-requests

No hay excepciones 'unsafe-inline' ni 'unsafe-eval'; los estilos en línea ya se habían trasladado a hojas de estilo. La política se envía dos veces: como etiqueta <meta> en cada página y como encabezado HTTP. Es intencional: los navegadores ignoran frame-ancestors en una etiqueta meta, así que la protección contra clickjacking solo funciona desde el encabezado.

La política también aplica Trusted Types sin permitir ninguna política (trusted-types 'none'). El navegador ahora se niega a convertir cualquier cadena de texto en HTML o en script: asignar a innerHTML, outerHTML o al texto de un script genera un error. Esto elimina el XSS basado en el DOM como categoría completa, no un error a la vez. Para lograrlo hubo que quitar todos esos puntos de inserción del código del propio sitio: la navegación y el pie de página compartidos ahora se construyen con las API del DOM, y el selector de idioma, que antes cambiaba el texto con innerHTML, ahora incluye ambos idiomas como marcado estático y deja que CSS muestre el activo.

06Dominio: correo y certificados

Este dominio nunca envía ni recibe correo, así que la política correcta es declararlo públicamente:

@        TXT  "v=spf1 -all"
_dmarc   TXT  "v=DMARC1; p=reject;"
@        CAA  0 issue "letsencrypt.org"
@        CAA  0 issue "pki.goog"
  • SPF -all no autoriza a ningún servidor a enviar correo en nombre del dominio.
  • DMARC p=reject indica a los proveedores que rechacen todo lo que no pase la verificación, en lugar de solo marcarlo.
  • CAA limita la emisión de certificados a las dos autoridades que usa mi proveedor de alojamiento. Incluir solo una habría hecho fallar una renovación futura a través de la otra.
  • DNSSEC ya estaba activado, así que estos registros están firmados y no pueden falsificarse en tránsito.

También quería un registro MX nulo (0 .) para declarar que el dominio no acepta correo. La interfaz del proveedor de DNS lo rechaza. Como SPF y DMARC ya cubren el riesgo de suplantación, documenté la limitación en lugar de cambiar de proveedor de DNS por ella.

07Implementación y verificación

El orden importaba. Endurecer el encabezado CSP antes de desplegar los recursos propios habría bloqueado las solicitudes a Google Fonts y jsDelivr en el sitio en vivo y habría roto todas las fuentes e íconos. Por eso la secuencia fue: publicar el código con la CSP estricta en la etiqueta <meta>, confirmar el despliegue y luego endurecer el encabezado. El cambio a Trusted Types siguió el mismo orden: el selector de idioma anterior dependía de innerHTML, así que aplicarlo en el encabezado antes de publicar el código reescrito habría roto la página.

  • Antes del despliegue: un navegador sin interfaz cargó cada página en modo claro y oscuro, en inglés y en español, en escritorio y en móvil, y verificó que no hubiera ninguna violación de la CSP, ningún error de JavaScript, ninguna solicitud a terceros, y que todas las fuentes e íconos cargaran correctamente. Para la reescritura de Trusted Types también comparó la versión anterior y la nueva lado a lado (mismo texto visible, mismo comportamiento de los selectores) y confirmó que el navegador ahora bloquea innerHTML por completo.
  • Después del despliegue: se revisaron directamente los encabezados de la respuesta en vivo y luego se evaluaron con el HTTP Observatory de Mozilla.
  • DNS: cada registro se confirmó mediante un resolutor público que valida DNSSEC.

08Próximos pasos

  • Precarga de HSTS. Evaluada y pospuesta. La precarga es prácticamente permanente y aporta poco frente a una política HSTS de dos años en un sitio sin inicios de sesión.
  • Seguridad de las cuentas. Tras este trabajo, el eslabón más débil ya no es el sitio, sino las cuentas detrás de él. Quien controle el repositorio Git, el proveedor de alojamiento o el registrador controla el sitio. Las tres cuentas están protegidas con autenticación multifactor, y ahí es donde debe centrarse la atención de aquí en adelante.
